# Let plugins ship in-app React UI built from ocman components

Plugin UI has so far been typed data rendered by the host. `pane.v1` contributes read-only trees, and `page.v1` grew in five protocol minors: forms with static rules and validation issues (1.1), collections, item details and pagination (1.1), plugin-local homepages (1.2), a native model picker (1.3), and summary cells, severity pills and right-hand drawers (1.4). Each step worked, but the limitation is structural. Every new visual (a different table layout, a second detail level, an inline status control) needs a host change, a protocol minor, an SDK release and a matching plugin release, and the plugin still cannot compose those pieces into its own workflow. The trust boundary was also misplaced. The native executable is fully trusted code running as the ocman user, yet its UI received no trust at all.

We add a second tier beside the declarative one. Tier one remains `page.v1`/`pane.v1`, the zero-JavaScript option that works on every owner. Tier two is in-app UI: a plugin that negotiates the `ui` capability (major 1) and holds the approved `ui.app` grant may declare `ui.exposes.index`, an ESM bundle whose default (or `Index`) export is a prop-less React component. ocman mounts it lazily at `/plugins/<id>/*` inside a per-plugin loader and error boundary. The plugin owns all sub-routing with nested relative `<Routes>` under the host router, never its own router. The manifest is a map of exposes, so later entry points such as `pane`, `settings` or `itemDrawer` need no protocol change; this release mounts only `index`. A first path segment that names a declared `page.v1` page still renders that page, so both tiers can coexist. A third tier, a sandboxed iframe for UI from remote owners, is future work.

Data access goes through the same machinery as other capabilities. `ui.v1` has two methods. `call` carries `{"method": <plugin-defined name>, "params": <json>}` and returns arbitrary JSON as one unary result. `bundle` streams the declared bytes as base64 chunks of at most 512 KiB, bounded to 4 MiB per bundle by the existing 1 MiB frame and 8 MiB per-call limits. The hub serves `GET /api/plugins/ui`, `GET /api/plugins/ui/bundle` and `POST /api/plugins/ui/call` through `RouteOperation` and the closed `PluginOperation` operations `ui-bundle` and `ui-call`. Calls are admitted under the lifecycle lock with the current grants and rechecked before results return, like panes and pages, and they create no durable receipts. Side-effecting work that needs confirmation or replay protection stays an `action.v1` action, which the UI runs through the host's action dialog.

Bundles load by `import(url)` from ocman's own origin, not through Module Federation. ocman's CSP is `script-src 'self'`, which blocks inline import maps, and plugin bundles must use the host's single React, router and query-client instances. The host build therefore emits stable entry modules at `/plugin-shared/<name>.js` for `react`, `react/jsx-runtime`, `react-dom`, `react-router-dom`, `@tanstack/react-query` and `@ocman/plugin-ui`. These entries re-export the same chunks the app uses; CommonJS packages get generated named exports, because `export *` loses them. The `@ocman/plugin-vite` preset builds a plugin as one ESM file with those specifiers external and rewritten to the URLs, refuses to bundle other subpaths of the same packages, inlines dynamic imports and assets, and injects imported CSS as one runtime `<style>` element, which `style-src 'unsafe-inline'` already permits. There is no sibling stylesheet in the manifest. Module Federation would add a runtime, a remote-entry protocol and shared-scope negotiation to solve the same problem. One host, a fixed singleton list and same-origin URLs make it unnecessary, and the result works unchanged in the Vite dev server, the Wails desktop app (which loads the same HTTP server) and through a hub.

The bundle's checksum and size are part of the description, so the approval fingerprint binds them. A changed bundle revokes approval like any changed declaration, and the host verifies streamed bytes against the approved checksum before serving them. In-app UI runs in ocman's origin with the user's ocman session. It can do anything the user can do in ocman, which is no more than the native process can already do on the machine. That holds only on the machine that approved the executable. In v1, therefore, the hub loads UI only for plugins executing locally. Remote owners keep their declarative views, and remote `ui-*` operations are refused rather than forwarded. Approval shows an explicit "this plugin runs UI code with your ocman session" disclosure together with the bundle checksum. Loading remote owners' UI, through a sandboxed iframe or an explicit cross-machine grant, is recorded as deliberate follow-up work.

`@ocman/plugin-ui` is a curated public package, not a re-export of `frontend/src/components`. It provides controls, tables, states, tabs, drawers, pickers, pills, layout primitives and the hooks `usePluginContext`, `usePluginCall`, `usePluginMutation` and `usePluginAction`. Each is wrapped with deliberate props, so internal components can change. Its published TypeScript declarations are the contract. The host implementation is type-checked against them, and a test keeps the runtime export list identical. The package is semver-versioned: additions are minor releases, and removals or changed meaning are major releases. Plugins declare the range they were built against as `ui.sdk`. The host compares it with its own version (`UISDKVersion`, kept equal to the package version by a test), lists incompatible plugins with an explanation and never imports their bundles.

Consequences: plugins can build arbitrary workflows from native components without host changes. The host now carries a public frontend API whose compatibility it must preserve across majors. Declarative pages remain the portable option, and in-app UI is a hub-local, higher-trust tier. Rebuilding a bundle requires re-approval because the checksum is in the description; a cheaper development loop, such as reloading bundles on rescan without full re-approval in an explicit development mode, remains follow-up work.
